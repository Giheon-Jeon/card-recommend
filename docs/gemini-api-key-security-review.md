# Gemini API 키 평문 브라우저 저장 보안 검토 및 완화 대책 보고서 (#25)

## 1. 개요 및 배경

본 보고서는 GitHub 이슈 #25(`[BUG] Gemini API 키 평문 localStorage 저장 보안 검토`)에 따라, 현재 웹 애플리케이션 내 Google Gemini API 키 보관 및 처리 방식에 대한 보안 위험도를 재평가하고, 적용된 완화 조치 및 향후 아키텍처 개선 방향을 정리한 문서입니다.

- **대상 컴포넌트**: `src/contexts/GeminiApiKeyContext.tsx`, `src/components/ApiKeySettings.tsx`, `src/components/SpendingImporter.tsx`
- **현상**: 사용자가 입력한 Gemini API 키가 브라우저 스토리지에 평문(Plaintext)으로 저장되어, 동일 오리진(Origin) 내 스크립트 실행 시 키 탈취 위험이 존재함.

---

## 2. 위험도 재평가 (개인 로컬 전용 도구 관점)

### 2.1 아키텍처 특성
본 프로젝트(`card-benefit-tracker`)는 별도의 중앙 백엔드 서버나 DB 없이, 정적 호스팅(Static SPA) 및 사용자의 로컬 브라우저 환경에서 동작하는 개인 최적화 도구입니다.

### 2.2 공격 벡터 분석
| 공격 벡터 | 발생 시나리오 | 기존 위험도 | 완화 후 위험도 |
| :--- | :--- | :---: | :---: |
| **XSS (크로스 사이트 스크립팅)** | 서드파티 스크립트 결함이나 취약 라이브러리를 통해 악성 JS가 실행되어 `localStorage` 탈취 | **High** | **Medium** (세션 스토리지 활용 시 노출 시간창 대폭 축소) |
| **공용 PC / 공용 브라우저 노출** | 공용 PC나 타인 대여 기기에서 사용 후 탭만 닫았을 때 `localStorage`에 영구 보관된 키 노출 | **High** | **Low** (세션 모드 사용 시 브라우저 탭 종료와 동시에 즉시 파기) |
| **악성 브라우저 확장 프로그램** | 웹페이지 DOM 및 스토리지 접근 권한을 가진 확장 프로그램에 의한 탈취 | **High** | **High** (클라이언트 사이드 태생적 한계) |
| **물리적 기기 탈취 / 개발자 도구 노출** | 기기 분실 또는 개발자 도구(F12) 콘솔 접근을 통한 확인 | **Medium** | **Low** (세션 모드 적용 및 불필요 시 즉시 삭제) |

## 3. 구현된 완화 대책 (Mitigation Measures)

### 3.1 세션 스코프 분리 및 선택 옵션 제공 (`sessionStorage` 지원)
- **세션 보관 (권장, Default)**:
  - 브라우저 탭/창을 닫으면 API 키가 메모리 스토리지에서 즉각 파기됩니다.
  - XSS 발생 시에도 공격자가 과거 세션의 키를 사후에 탈취할 수 없습니다.
- **로컬 보관 (선택)**:
  - 개인 신뢰 기기에서 매번 키를 재입력하기 번거로운 사용자를 위한 선택지로 제공하되, 위험성을 명확히 고지합니다.
- **스토리지 동기화 및 격리**:
  - 세션 모드 선택 시 기존 로컬 스토리지 키를 즉시 삭제하여 잔여 키 유출을 차단합니다.

### 3.2 UI 보안 안내 및 가이드라인 대폭 강화
- `ApiKeySettings` 컴포넌트에 **보안 주의 배너**(`ShieldAlert`)를 탑재하여 다음 내용을 상시 안내합니다:
  - "API Key는 별도의 백엔드 서버 없이 브라우저 내부에만 저장됩니다."
  - "XSS 위험 완화를 위해 공용 기기에서는 반드시 세션 보관을 권장합니다."
- 상태 뱃지("클라이언트 전용", "세션 보관(권장)")를 명시하여 사용자가 보안 의사결정을 주도할 수 있도록 지원합니다.

### 3.3 단위 테스트를 통한 스토리지 라이프사이클 검증
- `tests/GeminiApiKeyContext.test.tsx`:
  - `sessionStorage` 우선 로드, 모드별 상호 배타적 저장 및 삭제 동작 단위 검증
- `tests/ApiKeySettings.test.tsx`:
  - 보안 배너 렌더링, 라디오 변경 이벤트, 접근성 표준(Accessible Form Control) 검증

## 4. 향후 로드맵: 서버 프록시 방식 도입 검토

현재의 클라이언트 사이드 보관은 별도 서버 운영 비용이 들지 않는 장점이 있으나, 완전한 Zero-Trust 보안을 달성하기 위해서는 장기적으로 **서버 프록시(BFF / Serverless Proxy)** 아키텍처를 검토할 수 있습니다.

### 4.1 비교 분석
| 구분 | 현재 (클라이언트 스토리지 + Gemini 직접 호출) | 향후 (서버리스 프록시 + 유저 인증) |
| :--- | :--- | :--- |
| **키 관리 주체** | 사용자가 본인 Gemini API Key 발급 및 브라우저 보관 | 서버 환경변수(`GEMINI_API_KEY`)로 중앙 집중 관리 |
| **클라이언트 노출 여부** | 스토리지/네트워크 요청 헤더에 노출 가능 | 클라이언트에 키 노출 전혀 없음 (Zero Exposure) |
| **운영 비용** | 0원 (정적 호스팅 무료 티어) | 클라우드 함수 / API Gateway / 인증 서버 인프라 필요 |
| **사용자 편의성** | Google AI Studio 키 발급 절차 필요 | 별도 키 발급 없이 서비스 즉시 이용 가능 |

### 4.2 권장 결론
- 단기적으로는 이번에 적용된 **세션 스토리지 기반 격리 및 보안 안내 강화**로 대부분의 공용 기기 및 영구 노출 위험을 성공적으로 완화하였습니다.
- 서비스 사용자가 확대되거나 상용화 단계로 진입할 경우, Cloudflare Workers 또는 Vercel Serverless Function을 활용한 프록시 엔드포인트 도입을 권고합니다.
